Delivery is a sequence, not a ticket.

From business intent to a change that holds in production.

Name → calendar → prove → cut over

Methods are lanes. The chain stays open until the outcome is checked.

Illustrative sequence. A release is not complete until its outcome has been checked.

Tools sit inside this model. SDLC says how the software is engineered. This card says how the work is sequenced and the outcome is verified.

1 · What has to be true

Select a stage. The gate is the decision rule.

Intent · proceed only if

The outcome has an owner

What this change is for, and the person who owns it. A ticket title is not an outcome.

Intent is the outcome. The chain starts here.

Window · proceed only if

The clocks agree

Platform, security, and the business freeze, named as one window. A middleware patch waits for that window and a business-hours check.

Window is whose clock. Colliding calendars stop the signal.

Proof · proceed only if

The evidence is written

The dependency owner, the blast radius, and the metrics you will watch. A change that needs a cert rotation carries owner, blocker, and date on one plan.

Proof is the evidence. It exists before the call.

Cutover · proceed only if

Rollback is named before green

A named owner, the rollback steps, who gets paged, and the monitoring plan. Ship dark behind a flag when you must reverse without a weekend restore.

Cutover is the sequence and the rollback. Pipeline green is not this gate.

Observe · still open

The outcome is still open

Error rate and queue depth for a named window after cutover. Thirty minutes is the working example. The chain stays open until those signals say the change held.

Observe is whether it held.

Observe · held

The outcome is checked

The watched signals held for the window you named. The written rollback stays in reach.

Held means verified, and recoverable.

2 · When the sequence stops

Four situations. The rest of the jobs sit in the reference below.

Pick a situation. The chain stops on the gate that has to answer it.

Signal stops at window

Decision Change window A named window, with a check a person owns.
Evidence Freeze, then a business-hours check Both written down before anyone moves the patch.
Next The middleware patch waits It does not ship on a chat slot.

Signal stops at proof

Decision Dependency map Owner, blocker, and date on one plan.
Evidence Who owns the wait The cert rotation names the person, the blocker, and the date.
Next Status names the wait The change stays put until that owner is real.

Signal stops at cutover

Decision Done that survives the room Rollback and the page path, before anyone says green.
Evidence The change note carries the reverse Steps, and who gets paged, written in advance.
Next Tests passing is not held Write the reverse, then call the change.

Signal stops at observe

Decision Watch the service The signals you named, for the window you named.
Evidence Error rate and queue depth Thirty minutes after cutover is the working window.
Next Roll back on the written path The reverse already exists. Use it.

3 · What you measure

Flow says how the work moves. Outcome says whether it held.

  • Flow Lead time From named intent to the change in production.
  • Flow Change-failure rate How often a change is reversed or patched.
  • Outcome Recovery time How fast the written rollback returns the service.
  • Outcome Service health Whether the watched signals held after green.

Name them beside the four keys. Publish a figure only when this portfolio has measured it. Velocity stays off this path.

Ladder

  1. Named intent and owner
  2. Calendars and a dependency map
  3. Evidence pack: blast radius, metrics
  4. Rollback and page path written
  5. Small sequenced change, or a flag
  6. Watch whether it held
Kill switch If you can’t name the owner, the window, and how to reverse, you don’t call it green.

Status lives in a chat thread Visible work Blocker named on the board item; standup does not replace a written wait
Need fast feedback on main, not a long-lived branch Small batches on trunk Incomplete UI stays behind a flag; main stays releasable — Fowler’s CD test, not a two-week merge
Don’t know if delivery is actually getting healthier Four keys Lead time and change-fail rate next to the Azure ops pack; velocity theatre stays off this path

Anti-patterns

  • Ticket title as the outcome
  • Calling pipeline green with no rollback
  • Private AI speed as team capability
  • Shipping while calendars still collide
  • Chat-thread status with no named blocker
  • Automating priority or the “not yet” call
  • Long-lived branches instead of flags
  • Framework shopping (SAFe/Scrum) before sequence

The close

A change is not done when the pipeline turns green. It is done when the intended outcome is verified — and the team knows how to recover if it isn't.
